# Architecture — vshell

## 1. Concept

**Desktop** VS Code (Electron) cannot run outside Electron. What *does* run in any
browser/webview is the **web** build (`vscode-web`). Therefore:

- `vshell` is a **browser packaged with its own shell**, not an Electron runtime.
- The workbench (Monaco, layout, themes) is the same TS code as the web build.
- What the shell contributes is what the web build lacks: a native window, menus,
  tray, deep links, a secure store, auto-update.

## 2. The engine: why WebKit/JSC and not V8

| Engine | JS | Windows | Linux | macOS | Embeddable | Bindings from V | License |
|---|---|---|---|---|---|---|---|
| **Ultralight** | **JSC** | **✓** | **✓** | **✓** | ✓ (C API) | direct (C) | partly LGPL / commercial |
| WebKitGTK / WPE | JSC | ✗ | ✓ | ✗ | ✓ (C/GObject) | our own | LGPL/BSD |
| WKWebView | JSC | ✗ | ✗ | ✓ | ✓ (Obj-C) | `.m` shim | system |
| CEF | **V8** | ✓ | ✓ | ✓ | ✓ (C) | our own | BSD-ish |
| Gecko (Midori model) | SpiderMonkey | ✓ | ✓ | ✓ | ✗ (rebranded Firefox) | — | MPL |

Verified facts:

- **CEF uses V8** (it ships inside Chromium; it cannot be swapped without rebuilding
  Chromium).
- **Bun uses JavaScriptCore**, not V8 → if rendering is WebKit/JSC, the **whole stack
  is JSC**.
- **Ultralight** describes itself as *"a stripped-down, single-process,
  platform-agnostic port of WebKit designed for embedding"* and uses *"the same
  JavaScript engine as WebKit/Safari"* (JSC). Platforms: Windows x64, macOS, Linux
  (+ consoles). Official C API.
- **There is no modern WebKit for Windows**: MSYS2 only packages **QtWebKit
  5.212.0-alpha** (~2016, unmaintained). WebKit carries the **WinCairo** port in its
  tree, but with no modern embedding API (`Source/WebKit/win/` is WebKitLegacy).
- **Midori** moved from WebKitGTK to **Firefox/Gecko** by rebranding Firefox: proof
  that Gecko is cross-platform, but **not** that it is embeddable (GeckoView is
  Android-only; XULRunner is discontinued).

**MinGW** is the *compile/link* layer (V uses gcc/clang as its C backend): it lets you
write the binding. It does not provide the engine.

## 3. Communication

```
┌──────────────────────────────┐        ┌──────────────────────────────┐
│  Ultralight (WebKit + JSC)   │        │  Bun (JSC)                    │
│  workbench renderer          │  HTTP  │  vscode-reh-web               │
│  + JS <-> V bridge           │ <====> │  extension host, FS, PTY      │
└──────────────────────────────┘   WS   └──────────────────────────────┘
             ▲                                          ▲
             └──────────────  vshell.exe (V)  ──────────┘
                       launches Bun as a child, opens the window,
                       manages lifecycle, menus, updates
```

- No shared heap: **everything goes over HTTP/WS**. No objects are passed between
  engines.
- The REH connection token is generated by the shell and injected into the URL.

## 4. Why `vscode` is NOT a submodule here

`codibun/get_repo.sh` clones by SHA and `dev/patch.sh` runs `git reset --hard`, so the
vscode tree is **mutable and regenerable**. A submodule is for *pinning a tree you
edit*. Here we only **consume** vscode as a *build input* (to build `vscode-web`), so a
disposable clone in `.work/` is the right call.

If `vshell` ever needs to **patch** vscode, that changes: submodule (or codibun's
`patches/` pipeline).

## 5. JS ↔ V bridge

Two directions, both native:

- **V → JS:** `ulViewEvaluateScript(view, script, &exception)`. The result and the
  exception are **owned by the View**: destroying them is an invalid free and crashes
  the process. The exception is an *empty string* (not NULL) when nothing was thrown.
- **JS → V:** `ULJSAPI` (`Ultralight/CAPI/CAPI_JSAPI.h`). `ulCreateJSAPI("vshell")`
  plus `ulJSAPIBindFunction(api, "post", …)` and `ulJSAPISetConstantString(...)`
  register a namespace, and `ulViewAttachJSAPI(view, api, flags, origin_rules, n)`
  injects it into the page as a **frozen** `window.vshell` object.

Two non-obvious rules, both of which fail *silently*:

1. **Origin rules.** With the default rules the API only reaches `file://` pages and
   directly-loaded HTML. The workbench is served over `http://`, so it needs an
   explicit rule (`http://127.0.0.1:<port>`). Otherwise the namespace never appears —
   and `ulViewAttachJSAPI` still returns `true`.
2. **Attach before loading.** `ulViewAttachJSAPI` must run before `ulViewLoadURL`; an
   API attached later cannot add to a namespace the page has already frozen.

The callback runs on the renderer's thread while script executes, so it only appends to
a V-side inbox; the run loop drains it. That loop is `for C.ulAppRunOnce(app, 1.0/60.0)
{ pump() }` rather than `ulAppRun` + an update callback, because **evaluating JS from
inside the engine's update callback deadlocks**.

## 6. Licensing and risks

- **Ultralight**: only part of WebCore is LGPL on GitHub; the complete code is
  **Enterprise**. Review terms/price **before** building a product.
- It is a WebKit **fork**, not upstream: the VS Code web build has to be validated
  against it (Phase 0 of the roadmap).
- **Single-process, no** Chromium-style multi-process sandbox: a different security
  model.
- With no V8 there is no `v8` module, no `--js-flags`, and no extensions that assume
  V8. `Bun`/JSC covers this for the server, but not for Chromium-specific renderer
  APIs (e.g. the File System Access API) → the FS is served from the server instead.
- **V 0.5.2 toolchain**: the `src/` directory layout is no longer supported → sources
  live at the project root and `engine/` is a submodule. For the same reason the
  `ttytm.webview` fallback (v0.7.0, still using `src/`) is disabled.
