# Architecture — vshell

## 1. Concept

**Desktop** VS Code (Electron) cannot run outside Electron. What *does* run in any
browser/webview is the **web** build (`vscode-web`). Therefore:

- `vshell` is a **browser packaged with its own shell**, not an Electron runtime.
- The workbench (Monaco, layout, themes) is the same TS code as the web build.
- What the shell contributes is what the web build lacks: a native window, menus,
  tray, deep links, a secure store, auto-update.

## 2. The engine: why WebKit/JSC and not V8

| Engine | JS | Windows | Linux | macOS | Embeddable | Bindings from V | License |
|---|---|---|---|---|---|---|---|
| **WebKit (WinCairo)** ← *current* | **JSC** | **✓** | ✗ | ✗ | ✓ (WebKit2 **C API**, `UIProcess/API/C/win/`) | direct (C) | LGPL/BSD |
| Ultralight ← *legacy backend* | **JSC** | **✓** | **✓** | **✓** | ✓ (C API) | direct (C) | partly LGPL / commercial |
| WebKitGTK / WPE | JSC | ✗ | ✓ | ✗ | ✓ (C/GObject) | our own | LGPL/BSD |
| WKWebView | JSC | ✗ | ✗ | ✓ | ✓ (Obj-C) | `.m` shim | system |
| CEF | **V8** | ✓ | ✓ | ✓ | ✓ (C) | our own | BSD-ish |
| Gecko (Midori model) | SpiderMonkey | ✓ | ✓ | ✓ | ✗ (rebranded Firefox) | — | MPL |

Verified facts:

- **CEF uses V8** (it ships inside Chromium; it cannot be swapped without rebuilding
  Chromium).
- **Bun uses JavaScriptCore**, not V8 → if rendering is WebKit/JSC, the **whole stack
  is JSC**.
- **Ultralight** describes itself as *"a stripped-down, single-process,
  platform-agnostic port of WebKit designed for embedding"* and uses *"the same
  JavaScript engine as WebKit/Safari"* (JSC). Platforms: Windows x64, macOS, Linux
  (+ consoles). Official C API.
- **There *is* a modern WebKit for Windows: the WinCairo port**, built from the
  upstream `WebKit/WebKit` tree with `build-webkit --release` (x64 only, Cairo +
  libcurl, WebKit2 multi-process). Its embedding API is the WebKit2 C API in
  `Source/WebKit/UIProcess/API/C/` plus `UIProcess/API/C/win/WKView.h` — **not**
  `Source/WebKit/win/`, which is WebKitLegacy. Verified against `main` on
  2026-10-13; the canonical usage sample is `Tools/MiniBrowser/win/`.
- WinCairo is **not distributed as an SDK**: you build it yourself and stage it
  (`scripts/stage_runtime.sh`). It is built with MSVC/clang-cl and we link from
  mingw-w64 gcc through a MinGW import library (`gendef` + `dlltool`); both sides use
  UCRT, and the C API is `extern "C"` with undecorated names, which is what makes
  the mix work.
- A **WebKitGTK**-style API on Windows does not exist: WebKitGTK/WPE are Linux-only
  upstream ports, and MSYS2 only packages **QtWebKit 5.212.0-alpha** (~2016,
  unmaintained). That is a different thing from the WinCairo port.
- **Midori** moved from WebKitGTK to **Firefox/Gecko** by rebranding Firefox: proof
  that Gecko is cross-platform, but **not** that it is embeddable (GeckoView is
  Android-only; XULRunner is discontinued).

**MinGW** is the *compile/link* layer (V uses gcc/clang as its C backend): it lets you
write the binding. It does not provide the engine.

## 3. Communication

```
┌──────────────────────────────┐        ┌──────────────────────────────┐
│  WebKit2 / WinCairo (JSC)    │        │  Bun (JSC)                    │
│  workbench renderer          │  HTTP  │  backend service              │
│  + JS <-> V bridge           │ <====> │  FS, PTY, search, token       │
└──────────────────────────────┘   WS   └──────────────────────────────┘
             ▲                                          ▲
             └──────────────  vshell.exe (V)  ──────────┘
                       launches Bun as a child, opens the window,
                       manages lifecycle, menus, updates
```

- No shared heap: **everything goes over HTTP/WS**. No objects are passed between
  engines.
- The session token is generated by the shell and delivered **out of band**, never
  in a URL: see §3.3.

### 3.1 Which backend, and why the order matters

The workbench needs a backend for anything the web build cannot do alone: opening a
real folder, the integrated terminal, workspace search. There are two ways to give it
one, and they are **not** equivalent:

| | Own web extension + Bun service (**first**) | `vscode-reh-web` on Bun (**later**) |
|---|---|---|
| FS / PTY / search | we implement them (`FileSystemProvider`, `Pseudoterminal`) | VS Code already does |
| Extensions that run | **web extensions only** | **all**, including Node ones (Python, C++, ESLint) |
| Main risk | coverage and reach of a web-only extension host | Bun digesting `worker_threads`, `v8`/`inspector` and `.node` modules |

**Decision (2026-10-15):** ship the web-extension route first, because it is bounded
and keeps everything on Bun. `vscode-reh-web` is evaluated **case by case** afterwards;
if it turns out not to be complicated, the goal is still to run it on Bun — but the
web route must not depend on that outcome.

An earlier version of this section described `vscode-reh-web` as *the* backend. It is
the second route, not the first.

**First spike (2026-10-25):** the second route is much closer than the table suggests.
`bun build/next/index.ts bundle --target server-web` runs unchanged, the server boots
on Bun (`Web UI available`, `Extension host agent started`), and our WebKit window
renders the workbench it serves. What the web build cannot do — real `file:`, PTY,
search, watch, Node extensions — is *already written* in the Node half; the REH just
needs that half to run. The remaining work is build-side (native addons) and one
upstream bug, not engine-side. `scripts/build_reh.sh` reproduces the whole thing.

**The one seam that had to be built (2026-10-25):** the REH's WebSocket server is
VS Code's `ws` on `node:http`, and under Bun our WebKit never sees `open` — the
handshake is completed server-side with a correct `101`, then the client dies with
`1006` after ~10 s. WebKit ↔ `Bun.serve` works, and Bun as a *client* of the REH
works, so the shell now owns the origin and pipes the socket (`web/proxy.js`,
`--reh <url>`). That, plus forwarding `x-forwarded-host` (the source of the page's
`remoteAuthority`), is what finally let the **remote extension host start on Bun**.
It is a proxy, not a reimplementation: the protocol stays VS Code's.

### 3.2 Opening a folder: never through the URL

`vscode.openFolder` looks like the obvious way to implement "Open Folder" inside the
extension, and it is a trap. In the web build it does not open anything itself: it
hands the folder to `WorkspaceProvider.open`
(`src/vs/code/browser/workbench/workbench.ts`), which builds

    <origin><path>?folder=<encoded uri>

and assigns it to `location.href`. The page **reloads** with that folder as its
workspace, and that is where it breaks. `web.main.ts#initServices` resolves and
validates the workspace folder at the very start of startup — before the web worker
extension host has started, and therefore before any `onFileSystem:` extension can
register a provider. The workbench then reports

    Ignoring the error while validating workspace folder codebun:c:/... -
    Unable to resolve filesystem provider with relative file path 'codebun:c:/...'

drops the folder, reloads once more to retry, and the race repeats on the new page.
What the user sees is a permanently **blank** workbench: the page is reloading in a
loop, not failing to render. It is the workbench's startup order, not the WebKit
port — the same artifact behaves the same in Chromium.

**Decision (2026-10-15):** the folder is added to the window that is already open,
with `vscode.workspace.updateWorkspaceFolders`, from the extension. The extension is
necessarily running at that point — it is the one executing the command — so the
provider exists before the folder does. No race, and a single-view shell does not pay
a page reload (nor the `handleExpectedShutdown` errors that come with it) just to
change folder.

The trade-off, stated plainly: the folder is not part of the URL, so a reload loses
it. When the shell owns the last-opened folder it will persist it and add it back
after activation — **not** by putting it back in the URL, which is the failing path
above.

### 3.3 Session bootstrap: token and folder, out of band

Both values are known before the window exists and must reach the *page* before the
first document runs, so they cannot travel as an HTTP response and must not travel in
the URL (a URL is logged, cached and fetchable by any local process; §3.2 shows what
happens when state is threaded through `location.href`). The engine injects them as a
`WKUserScript` at document start (`engine/webkit.v`, `build_user_script`):

```
window.__codebunBootstrap = { token, folder }      // inspection / debugging
BroadcastChannel("codebun-bootstrap").postMessage({ type: "codebun:bootstrap", ... })
```

The extension host worker listens on the same channel, and repeats its `hello` every
250 ms until a reply arrives — a channel has no replay, and either side may start
after the other. From then on the token rides on every request as
`X-Codebun-Token`; the terminal passes the same secret as `?token=` because a
`WebSocket` built by the page cannot set headers. `web/backend.js` checks the token
before routing anything, so the check is inherited by every endpoint that is added
later.

The page also relays `codebun:pickFolder` to the shell, which answers with
`window.vshell.call("dialog.openFolder")` → the native `IFileOpenDialog`
(`engine/wk_host.h`). The dialog is therefore reachable from the workbench even
though the web build's own picker expects a remote authority.

Note what this boundary is and is not: it is “the engine delivered the page”, not
isolation from a local process that can already run script in that origin. With no
token set (standalone `bun run web/serve.js`) the service is open, on purpose.

## 4. Why `vscode` is NOT a submodule here

`codebun/get_repo.sh` clones by SHA and `dev/patch.sh` runs `git reset --hard`, so the
vscode tree is **mutable and regenerable**. A submodule is for *pinning a tree you
edit*. Here we only **consume** vscode as a *build input* (to build `vscode-web`), so a
disposable clone in `.work/` is the right call.

If `vshell` ever needs to **patch** vscode, that changes: submodule (or codebun's
`patches/` pipeline).

## 5. JS ↔ V bridge

Two directions, both native:

- **V → JS:** `ulViewEvaluateScript(view, script, &exception)`. The result and the
  exception are **owned by the View**: destroying them is an invalid free and crashes
  the process. The exception is an *empty string* (not NULL) when nothing was thrown.
- **JS → V:** `ULJSAPI` (`Ultralight/CAPI/CAPI_JSAPI.h`). `ulCreateJSAPI("vshell")`
  plus `ulJSAPIBindFunction(api, "post", …)` and `ulJSAPISetConstantString(...)`
  register a namespace, and `ulViewAttachJSAPI(view, api, flags, origin_rules, n)`
  injects it into the page as a **frozen** `window.vshell` object.

Two non-obvious rules, both of which fail *silently*:

1. **Origin rules.** With the default rules the API only reaches `file://` pages and
   directly-loaded HTML. The workbench is served over `http://`, so it needs an
   explicit rule (`http://127.0.0.1:<port>`). Otherwise the namespace never appears —
   and `ulViewAttachJSAPI` still returns `true`.
2. **Attach before loading.** `ulViewAttachJSAPI` must run before `ulViewLoadURL`; an
   API attached later cannot add to a namespace the page has already frozen.

The callback runs on the renderer's thread while script executes, so it only appends to
a V-side inbox; the run loop drains it. That loop is `for C.ulAppRunOnce(app, 1.0/60.0)
{ pump() }` rather than `ulAppRun` + an update callback, because **evaluating JS from
inside the engine's update callback deadlocks**.

### The bridge with the WebKit backend

- **V → JS:** `WKPageEvaluateJavaScriptInMainFrame(page, script, ctx, cb)`. This is
  **asynchronous**, so `eval_js()` keeps its synchronous-looking interface by pumping
  the message loop until the callback fires (3 s timeout). Consequence: never call it
  from inside a WebKit callback (message handler, page client) — it re-enters the UI
  process and hangs. Same trap as Ultralight's update callback, different costume.
- **JS → V:** `WKUserContentControllerAddScriptMessageHandler(ucc, "vshell", …)` on
  the page configuration, plus a `WKUserScript` injected at *document start* that
  defines the frozen object as `window.webkit.messageHandlers.vshell.postMessage(…)`.
  Two differences from `ULJSAPI`: there are **no origin rules** (the `http://`
  workbench works with no extra configuration), and `WKScriptMessageRef` exposes
  **no name getter** — only `WKScriptMessageGetBody`. So the page packs
  `name + "\x1f" + payload` into one string and V splits on the separator.
- **V → JS results** are a `WKTypeRef`, not necessarily a string, and `wk_type_to_utf8`
  only converts `WKString` — any other value (number, object, `undefined`) arrives as
  `''`, with no error. So a script whose value matters must return a string itself
  (`JSON.stringify(...)`, or a ternary — the readiness probe in `pump()` does exactly
  that).
- **The eval callback never reports an exception.** `WKPageEvaluateJavaScriptInFrame`
  ends with `if (result) callback(…, nullptr, …); else callback(nullptr, nullptr, …)`
  (`Source/WebKit/UIProcess/API/C/WKPage.cpp`), so a thrown exception, a syntax error
  and a cancelled evaluation all arrive as `(NULL, NULL)` — indistinguishable from an
  empty result. `eval_js_checked()` works around it by `eval`-ing the script inside a
  `try/catch` and returning the message as a value; `eval_js()` stays raw because the
  internal probes want the plain string.
- **`eval` needs one command-line argument.** On Windows the script is split on
  spaces before V sees it, which is why a probe written `typeof window.X` used to
  answer with an empty line: what ran was `typeof`.
- **The window is ours.** `WKViewCreate(RECT, WKPageConfigurationRef, HWND)` takes a
  `RECT` **by value** and returns a child view, so `engine/wk_host.h` creates the frame
  (`WNDCLASSW` + `CreateWindowExW`, resizing the child on `WM_SIZE`) and `run()` is a
  plain `PeekMessage`/`TranslateMessage`/`DispatchMessage` pump that idles on
  `MsgWaitForMultipleObjectsEx` (~0% CPU). `pump()` still runs from V between messages.

- **Page state is pushed, not polled.** `WKPageSetPageStateClient` (version 0) reports
  `didChangeTitle` / `didChangeActiveURL`; the callbacks only set a bit in the host
  state and V reads the values on its next pump tick. Two reasons it is done this way:
  reading `WKPageCopyTitle` on a timer is a synchronous IPC round-trip per poll, and
  calling *anything* into WebKit from inside a client callback re-enters the UI process
  (the same trap as the message handler).
  Note this C client has no equivalent of `WKPageIsLoading`, so "the document is
  ready" stays a `document.readyState` poll; `didChangeIsLoading` cannot be turned
  into a state because no getter exposes which way it changed.

- **The menu bar is `CreateMenu()`, not `CreatePopupMenu()`.** `SetMenu` rejects a
  popup handle with `ERROR_INVALID_PARAMETER` (87) and the window silently ends up
  without a menu — measured, after the first version looked correct in every way
  except the pixels. Menu commands are dispatched from `pump()`, never from the
  `WM_COMMAND` handler, because `run_menu_command` evaluates JS.

## 6. The extension host on Bun

The REH route (`ROADMAP.md`, Phase 2b) inherits VS Code's own Node-half services, so
the only interesting question is whether its extension host can run on Bun. It can,
but two Bun gaps sit exactly on the path and both fail **silently** — they produce no
error the shell can see, only an extension host that does nothing.

- **The transport.** The server hands its socket to the forked child with
  `child.send(msg, socket)`. Bun carries the *message* and drops the *handle*:
  instrumenting the child showed
  `ipc message: {"type":"VSCODE_EXTHOST_IPC_SOCKET", "hasHandle":false}`. The child then
  waits for `VSCODE_EXTHOST_IPC_SOCKET` for 60 s and exits with code 0, having
  activated nothing. VS Code has a second transport for exactly this case — listen on a
  named pipe and let the child connect — and Bun's `node:net` speaks Windows named
  pipes (`net.createServer().listen('\\\\.\\pipe\\x')` works; what does *not* is
  `node:http` listening on one). So `configure_vscode_for_bun.sh` flips
  `_canSendSocket` off under Bun and the pipe transport takes over.
- **`require('vscode')`.** The interceptor resolves the API module with
  `module.registerHooks` (Node 22) or by patching `module._load`. Bun has neither:
  `registerHooks` is `undefined` and a `_load` patch is never consulted, so every
  `require('vscode')` in every extension throws `MODULE_NOT_FOUND`. What every runtime
  does honour is ordinary `node_modules` resolution, so the extension host writes a
  real `vscode` package into `<each extensions root>/node_modules/vscode/`; it hands
  `module.parent.filename` back through a global, which preserves the per-extension API
  instance the hooks used to provide. Built-in extensions are consumed as CommonJS
  (`typescript-language-features/dist/extension.js` has 89 `require("vscode")`), which
  is what the generated package serves.

Verification is a file, not a log, because the extension host's output goes to the
client: a probe extension that appends to `.work/node-probe.log` on module load and
again on activation now writes both lines, with
`execPath = bun.exe` and `versions.bun = 1.4.3`.

## 7. Licensing and risks

- **WebKit (WinCairo), the current engine**: LGPL-2.1 + BSD upstream, **no commercial
  edition**, and it is *upstream* — security fixes flow from WebKit directly. Keep
  `WebKit2.dll` as a separate DLL (the usual LGPL arrangement: ship the licence texts
  and publish your patches if you patch the engine).
- **Multi-process** (UIProcess + WebProcess + NetworkProcess): a stronger security
  model than Ultralight's single process, paid for with a bigger payload and a runtime
  layout that must ship the helper executables — a missing one shows up as a blank
  page with no error.
- **Ultralight (legacy backend)**: only part of WebCore is LGPL on GitHub; the
  complete code is **Enterprise**. Review terms/price before shipping anything that
  includes it.
- With no V8 there is no `v8` module, no `--js-flags`, and no extensions that assume
  V8. `Bun`/JSC covers this for the server, but not for Chromium-specific renderer
  APIs (e.g. the File System Access API) → the FS is served from the server instead.
- **V 0.5.2 toolchain**: the `src/` directory layout is no longer supported → sources
  live at the project root and `engine/` is a submodule. For the same reason the
  `ttytm.webview` fallback (v0.7.0, still using `src/`) is disabled.
